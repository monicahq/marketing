Een nieuwe functie kan waarde toevoegen. De code eronder voegt verantwoordelijkheid toe.

Iemand moet haar begrijpen, nakijken, testen, de berichten vertalen die ze introduceert en haar repareren wanneer een afhankelijkheid verandert. Uiteindelijk kan die iemand ik zijn, op een zondag waarop ik letterlijk iets anders had gepland.

Daarom vind ik het aantal regels dat aan Monica wordt toegevoegd niet bijzonder indrukwekkend.

### De rekening komt later

Stel je twee manieren voor om hetzelfde stukje persoonlijke informatie weer te geven. De ene past in een bestaand concept. De andere voegt eigen schermen, rechten, achtergrondtaken en instellingen toe.

De tweede aanpak kan gerechtvaardigd zijn. Maar we moeten het voordeel kunnen benoemen, want al die bewegende delen zijn nu van het project.

Dit wordt nog relevanter nu code genereren goedkoop is. Een hulpmiddel kan snel een grote implementatie produceren, zonder dat het resultaat daarmee goedkoop te begrijpen of veilig te onderhouden wordt.

Nuttig gedrag roekeloos verwijderen is niet het antwoord. [Functies verwijderen](/nl/handboek/removing-features/) vraagt zorg voor de mensen die erop vertrouwen. Het beste moment om onnodige code te vermijden is voordat we de verplichting aangaan.

Een korte oplossing is evenmin automatisch goed. Tien onbegrijpelijke regels kunnen meer werk zijn dan vijftig voor de hand liggende.

Ik wil genoeg code om Monica nuttig en begrijpelijk te maken. Ik wil geen grote verzameling code die slechts bewijst dat we heel druk waren. De repository is geen klantenkaart. We krijgen geen gratis broodje na een miljoen regels.
