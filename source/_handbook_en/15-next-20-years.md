A note about someone's favourite cake might be useful next week. A story about your grandmother might matter much more in twenty years.

That's an unusual timescale for software. The industry gets excited about a JavaScript framework for approximately the length of time it takes to install it. Meanwhile, your grandmother's story hasn't changed its build system once.

We want Monica to work on the timescale of the information people put into it.

### Longevity has consequences

It makes maintenance important. It makes understandable code important. It makes [being able to leave](/en/handbook/leaving/) important, because a memory shouldn't depend entirely on whether we still feel like maintaining a particular application.

It also means thinking beyond the original authors. Could another developer understand why a relationship works this way? Could someone operate the software without asking me what a mysterious setting means?

Open source makes that possible in a way closed code doesn't. It doesn't make it automatic. An abandoned repository with impossible installation instructions is still an abandoned repository.

Twenty years is an ambition, not a hosting guarantee. I can't promise what my life, the internet, or Monica will look like then. I can prefer decisions that leave more possibilities open.

The question isn't whether a feature looks modern today. It's whether the information it holds can remain useful after the fashion has passed. There will be plenty of fashions. Ideally, fewer lost memories.
