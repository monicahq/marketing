If something goes wrong with software holding personal information, it's understandable to want an answer quickly.

It's also important that we don't imply there is a round-the-clock support team behind Monica when [the introduction](/en/handbook/project/) explicitly explains that there isn't.

The project is maintained around other work and ordinary life. That shapes what people should expect.

### Be useful with the time available

A clear report makes it easier to investigate. Include the version, the task, what happened, and steps to reproduce the problem where possible. [The feedback article](/en/handbook/feedback/) has more detail.

Please don't send a copy of your private database to explain a confusing field. Invented examples and carefully redacted messages are safer starting points.

We should distinguish a serious problem affecting access or information from a request for a new feature. Both can matter, but they don't have the same urgency.

We should also be honest when something isn't supported or when we don't know the answer. A confident guess can waste more of someone's time than a straightforward limitation.

This isn't a response-time commitment, and it doesn't replace any specific service terms. It describes the kind of interaction we want within the capacity we have.

Limited capacity doesn't justify rudeness. On either side. The person asking needs help, and the person answering is a person too. It seems a useful principle for software about relationships.
