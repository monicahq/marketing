Это ещё одна статья серии **Building Monica**, где я пишу о том, как мы с нуля пересобираем Monica. Большинство статей этой серии, скорее всего, будут о самом продукте: об отношениях, напоминаниях, настройке, занятиях, приватности и обо всех вопросах, которые возникают, когда пытаешься описать жизнь людей в программе. Но при пересборке большого приложения по пути появляются и вещи поменьше. [LaraDB](https://github.com/monicahq/laradb) одна из них.

Работая над Monica v3, я обнаружил, что очень много времени смотрю прямо в базу данных. Для разработки приложения на Laravel это обычное дело. Вы создаёте контакт и проверяете, что записалось. Создаёте отношение и смотрите связанные строки. Меняете напоминание и проверяете даты. Запускаете действие, обновляете данные, переходите по внешнему ключу и повторяете это много раз за день.

Хороших способов сделать это уже немало. Tinker полезен, но не прост и не быстр в использовании. Такие приложения, как TablePlus, DBeaver, phpMyAdmin или Adminer, могут быть очень полезны, но не для быстрой проверки. Я регулярно пользуюсь [TablePlus](https://tableplus.com/), особенно когда нужно писать запросы, редактировать данные или подробно изучать схему. Но большую часть времени при разработке Monica мне не нужен был инструмент управления базой данных. Мне хотелось только быстро увидеть, что лежит в базе, не выходя из приложения, в котором я уже работаю.

С этой идеи и начался LaraDB. Установите зависимость для разработки, откройте `/db` и увидите базу данных.

```bash
composer require --dev monicahq/laradb
```

Всё устроено очень просто. Таблицы показаны слева, строки справа, а страница работает внутри самого приложения на Laravel. LaraDB поддерживает SQLite, MySQL и MariaDB, а также PostgreSQL.

## Браузер, а не менеджер базы данных

Самым важным нашим решением было оставить LaraDB только для чтения. В нём нет кнопки редактирования, кнопки удаления, формы вставки и SQL-консоли. Оба маршрута, которые добавляет пакет, это GET-маршруты, а сам пакет выполняет только запросы `SELECT`.

Отчасти это решение о безопасности, но в основном о границах задачи. Зрелых инструментов для управления базами данных уже достаточно, и воспроизведение части их возможностей внутри Laravel не сделало бы LaraDB полезнее для той задачи, которую мы решали.

Небольшой инструмент остаётся понятным, если у него очень чёткая работа. LaraDB должен отвечать на вопрос, что сейчас лежит в базе данных и как эти строки связаны друг с другом. Заменять полноценный клиент базы данных он не должен.

## Что нам в итоге понадобилось

Интерфейс отражает эти узкие рамки. LaraDB перечисляет таблицы текущей схемы и показывает их строки в плотной таблице. Видны типы столбцов, отмечены первичные и внешние ключи, значения `NULL` визуально отличаются от пустых строк, а длинные значения обрезаются, чтобы большие текстовые столбцы или столбцы JSON не делали страницу непригодной для работы.

Внешние ключи оказались одной из самых полезных для Monica возможностей. Если столбец ссылается на другую таблицу, по его значению можно перейти напрямую. Клик открывает связанную таблицу, отфильтрованную по нужной строке. Для Monica v3 это особенно полезно, потому что всё больше областей представлено явными связями между несколькими таблицами, а не большими самодостаточными записями.

Страница также показывает сведения о текущей базе данных и запросе. В зависимости от того, что предоставляет СУБД, LaraDB может показать тип и версию СУБД, имя базы данных, размер, число индексов и другие метаданные, специфичные для конкретной СУБД. Для текущей страницы он также показывает SQL-запрос, который дал результат, и время его выполнения.

Есть и JSON-представление таблицы. Добавить его было недорого, когда слой работы с базой данных отделили от HTML-отображения, и оно оказалось полезным для просмотра данных за пределами самой страницы.

Фронтенд намеренно автономен. Пакет поставляется со своими CSS и JavaScript и не зависит от сборки ресурсов в приложении, куда его ставят. Установка LaraDB не должна требовать настройки Tailwind, зависимости от Alpine или ещё одного шага сборки в существующем проекте.

## Настоящей работой стала абстракция над базами данных

Показать строки в браузере несложно. А вот единообразная поддержка SQLite, MySQL и PostgreSQL оказалась тем местом, где происходила большая часть интересной работы.

СУБД сильно различаются в том, как раскрывают схему и метаданные. Для перечисления таблиц, описания столбцов, поиска первичных ключей, разбора внешних ключей, подсчёта строк и получения сведений о самой базе данных нужны разные запросы в зависимости от СУБД. Даже такие детали, как экранирование идентификаторов, нужно обрабатывать правильно, а не считать универсальной операцией SQL.

LaraDB прячет эти различия за небольшим интерфейсом драйвера. Слой Laravel запрашивает таблицы, столбцы, строки и метаданные, не зная, SQLite, MySQL или PostgreSQL стоит за соединением.

Упрощённая часть контракта выглядит так:

```php
public function listTables(): array;

public function getColumns(string $table): array;

public function getRowCount(
    string $table,
    ?RowFilter $filter = null,
): int;

public function getRows(
    string $table,
    int $page,
    int $perPage,
    ?RowFilter $filter = null,
): TablePage;

public function getForeignKeys(string $table): array;
```

Каждый драйвер базы данных реализует эти операции по-своему, а остальная часть LaraDB работает с общими объектами результата, которые возвращает интерфейс.

Интересное следствие такого устройства в том, что основной код чтения базы данных вообще не зависит от Laravel. Он работает напрямую с PDO. Laravel отвечает за обнаружение пакета, конфигурацию, маршрутизацию и отрисовку, а сама инспекция базы данных может использоваться отдельно.

```php
use LaraDb\DriverFactory;

$pdo = new PDO('sqlite:database.sqlite');
$driver = DriverFactory::fromPdo($pdo);

foreach ($driver->listTables() as $table) {
    echo $table->name;
}
```

## Только чтение не значит безвредно

Раз пакет работает только на чтение, он не может испортить базу данных, но это не делает безвредным сам доступ к ней. Браузер базы данных может показать каждую строку каждой таблицы любому, кто до него доберётся, и для такого приложения, как Monica, это, очевидно, серьёзная проблема.

Поэтому LaraDB рассчитан на установку как зависимость для разработки.

```bash
composer require --dev monicahq/laradb
```

Обычное развёртывание в продакшене с `composer install --no-dev` этот пакет не включит. Кроме того, по умолчанию LaraDB отключён вне окружения `local`, а когда его маршруты включены, они по умолчанию используют middleware `web` и `auth`.

## Мелочи, которые рождаются при большой пересборке

Начиная серию Building Monica, я ожидал, что писать в основном придётся о больших архитектурных и продуктовых решениях, лежащих в основе Monica v3. Так и будет. Но я хочу также рассказывать о небольших инструментах и идеях, которые рождаются по ходу пересборки, потому что они тоже часть работы.

LaraDB не главная часть Monica v3 и не пытается стать крупным продуктом сам по себе. Это просто небольшой инструмент для разработки, который избавил нас от постоянной помехи. Пакет полезен именно потому, что его область ограничена, и мне хочется, чтобы так и осталось.

Если вы работаете с приложениями на Laravel и часто открываете клиент базы данных только для того, чтобы посмотреть, что только что записал ваш код, LaraDB может пригодиться и вам.

```bash
composer require --dev monicahq/laradb
```

Затем откройте `/db`.

Исходный код доступен по адресу [github.com/monicahq/laradb](https://github.com/monicahq/laradb).
