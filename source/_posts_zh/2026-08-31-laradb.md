这是 **Building Monica** 系列的又一篇文章，我在这个系列里记录从零重建 Monica 的过程。这个系列的大多数文章可能都会谈产品本身：关系、提醒、自定义、活动、隐私，以及在软件中表示人们生活时遇到的所有问题。但重建一个大型应用的同时，也会顺带产出一些更小的东西。[LaraDB](https://github.com/monicahq/laradb) 就是其中之一。

在开发 Monica v3 的过程中，我发现自己花了很多时间直接查看数据库。这在构建 Laravel 应用时并不稀奇。你创建一个联系人，检查写入了什么。你创建一段关系，查看相关的行。你修改一个提醒，核对日期。你执行一个操作，刷新数据，顺着外键跳转，一天里要把这个过程重复很多次。

已经有很多不错的办法可以做到这一点。Tinker 有用，但用起来既不简单也不快。TablePlus、DBeaver、phpMyAdmin 或 Adminer 这样的应用也非常有用，但不适合快速查一下。我经常使用 [TablePlus](https://tableplus.com/)，尤其是需要写查询、编辑数据或仔细查看结构的时候。但在开发 Monica 的大多数时候，我并不需要一个数据库管理工具，我只是想在不离开当前所用应用的前提下，快速看看数据库里有什么。

这就是 LaraDB 最初的想法。安装一个开发依赖，访问 `/db`，就能看到数据库。

```bash
composer require --dev monicahq/laradb
```

你得到的东西非常简单：左边是数据表，右边是数据行，页面就运行在 Laravel 应用内部。LaraDB 支持 SQLite、MySQL 和 MariaDB，以及 PostgreSQL。

![LaraDb 显示 value_list_items 表：左侧是 41 张表的列表，右侧是它们的行，外键列显示为可以点击跳转的链接。](/assets/images/blog/2026-08-31-laradb.webp)

## 是浏览器，而不是数据库管理工具

我们做出的最重要的决定，是让 LaraDB 保持只读。它没有编辑按钮、删除按钮、插入表单，也没有 SQL 控制台。这个包暴露的两个路由都是 GET 路由，并且只会执行 `SELECT` 语句。

这在一定程度上是出于安全考虑，但主要还是关乎范围。管理数据库已经有了成熟的工具，在 Laravel 里重现它们的部分功能，并不会让 LaraDB 对我们想解决的问题更有用。

一个小工具只要职责非常明确，就能保持易于理解。LaraDB 的目的是回答数据库里现在有什么，以及这些行之间有什么关联。它并不打算取代一个正经的数据库客户端。

## 我们最终需要什么

界面反映了这个狭窄的范围。LaraDB 列出当前结构中的数据表，并以紧凑的表格显示其中的行。它会显示列的类型，标出主键和外键，让 `NULL` 值在视觉上区别于空字符串，并截断过长的值，这样大段文本或 JSON 列不会让页面无法使用。

事实证明，外键是对 Monica 最有用的功能之一。如果某一列引用了另一张表，就可以直接顺着它的值跳转。点击后会打开被引用的表，并筛选出对应的行。这在 Monica v3 中尤其有用，因为越来越多的领域是通过多张表之间的显式关系来表示的，而不是通过庞大而自成一体的记录。

页面还会展示当前数据库和查询的一些上下文。根据数据库引擎能提供的信息，LaraDB 可以显示引擎和版本、数据库名称、大小、索引数量，以及其他特定于引擎的元数据。对于当前页面，它还会显示生成该结果的 SQL 语句，以及查询花了多长时间。

此外还有一张表的 JSON 表示。一旦把数据库层和 HTML 渲染分开，加上这个功能的成本就很低，而且在页面之外查看数据时事实证明很有用。

前端是有意做成自包含的。这个包自带 CSS 和 JavaScript，不依赖宿主应用的资源管线。安装 LaraDB 不应该要求在现有项目里添加 Tailwind 配置、Alpine 依赖或另一个构建步骤。

## 数据库抽象才是真正的工作

在浏览器里显示行很简单。真正有意思的工作，大多出在如何一致地支持 SQLite、MySQL 和 PostgreSQL 上。

各个引擎暴露结构和数据库元数据的方式差别很大。列出数据表、描述列、查找主键、解析外键、统计行数，以及获取数据库层面的信息，都需要根据引擎使用不同的查询。就连标识符的引用这样的细节，也需要正确处理，而不能当作通用的 SQL 操作。

LaraDB 把这些差异隐藏在一个小小的驱动接口之后。Laravel 这一层只需要请求数据表、列、行和元数据，而不必知道底层连接是 SQLite、MySQL 还是 PostgreSQL。

这份约定的简化版本大致如下：

```php
public function listTables(): array;

public function getColumns(string $table): array;

public function getRowCount(
    string $table,
    ?RowFilter $filter = null,
): int;

public function getRows(
    string $table,
    int $page,
    int $perPage,
    ?RowFilter $filter = null,
): TablePage;

public function getForeignKeys(string $table): array;
```

每个数据库驱动以不同的方式实现这些操作，而 LaraDB 的其余部分则使用接口返回的通用结果对象。

这个设计带来的一个有趣结果是：核心的数据库读取代码完全不依赖 Laravel，它直接使用 PDO。Laravel 负责包的发现、配置、路由和渲染，而真正的数据库检查可以单独使用。

```php
use LaraDb\DriverFactory;

$pdo = new PDO('sqlite:database.sqlite');
$driver = DriverFactory::fromPdo($pdo);

foreach ($driver->listTables() as $table) {
    echo $table->name;
}
```

## 只读不等于无害

这个包是只读的，可以防止它损坏数据库，但这并不意味着暴露数据库就是无害的。数据库浏览器可以向任何能访问它的人展示每张表里的每一行，对 Monica 这样的应用来说，这显然是个严重的问题。

因此，LaraDB 被设计为作为开发依赖来安装。

```bash
composer require --dev monicahq/laradb
```

使用 `composer install --no-dev` 的正常生产部署不会包含这个包。LaraDB 默认在 `local` 环境之外也是禁用的，启用后，它的路由默认使用 `web` 和 `auth` 中间件。

## 一次大重建中冒出的小东西

当我开始写 Building Monica 系列时，我原本以为大部分内容会集中在 Monica v3 背后的重大架构和产品决策上。这一点仍然不会变。但我也想记录下重建过程中产生的一些较小的工具和想法，因为它们同样是工作的一部分。

LaraDB 并不是 Monica v3 的重要组成部分，它也不打算自己成为一个重要的产品。它只是一个小小的开发工具，消除了我们反复遇到的一个烦恼。这个包之所以有用，恰恰是因为它的范围有限，我希望一直保持这样。

如果你开发 Laravel 应用，并且经常只为了看看代码刚写入了什么就打开数据库客户端，LaraDB 也许对你同样有用。

```bash
composer require --dev monicahq/laradb
```

然后访问 `/db`。

源代码在 [github.com/monicahq/laradb](https://github.com/monicahq/laradb)。
