拒绝别人的工作，感觉很不好。他们花了自己的时间想让 Monica 变得更好，而我们通常更愿意说声谢谢，然后合并。

但 pull request 不只是送来一份代码。它是一个提案，关乎我们之后要为之负责的产品。

有时代码很好，提案却依然不合适。

### 也要审查责任

一个集成今天可能运行得很漂亮，却让我们此后要为一个我们不想追踪多年的外部服务负责。一个新的设置可能解决了某个人的问题，却让一个本来就难用的界面对其他所有人更难用。

一个功能也可能与 [Monica 的用途](/zh/handbook/where/)相冲突。无论实现得多优雅，好友排行榜也不适合放进来。

可能的话，我们应该说明拒绝的理由。“这不属于产品，因为……”，比让贡献者去猜是他们的代码、他们的想法，还是他们这个人得罪了我们，要有用得多。

更小的贡献和早期的交流，可以减少白费的力气。它们不保证被接受。讨论可能暴露出我们起初谁都没看到的复杂性。

我们也应该愿意说出，问题出在我们自己的精力上。一个被无限期搁置的 pull request，不一定比一个坦率的拒绝更友善。

即使某次改动没有被合并，[贡献](/zh/handbook/contributing/)也应该是值得的。一次好的审查，可以澄清问题，建议一个更小的做法，或者解释一条边界。它不该变成一场比谁更用心的竞赛。
