Sie müssen kein PHP schreiben, um Monica besser zu machen.

Ein klarer Fehlerbericht kann Stunden sparen. Eine Übersetzung kann das Produkt für jemanden nutzbar machen, der sonst Schwierigkeiten damit hätte. Die Erklärung eines verwirrenden Ablaufs kann ein Problem aufdecken, das wir seit Monaten nicht mehr bemerken.

Das sind Beiträge, auch wenn GitHub nicht allen ein hübsches grünes Quadrat dafür gibt.

### Dort anfangen, wo das Projekt steht

Für Code lesen Sie bitte vor dem Start die Beitragsanleitung im aktuellen Repository. Sie ist für Einrichtungsdetails die bessere Quelle als ein Artikel, der drei Entwicklungsumgebungen überdauern kann.

Bei einer größeren Funktion besprechen Sie zuerst das Problem. [Unser Artikel über Priorisierung](/de/handbuch/prioritize/) erklärt, warum eine funktionierende Implementierung nicht automatisch etwas ist, das wir pflegen können. Das herauszufinden, bevor man zwei Wochenenden darauf verwendet hat, ist für alle besser.

Dokumentation und Übersetzungen verdienen dieselbe Sorgfalt wie Code. Prüfen Sie, was die Oberfläche tatsächlich tut. Bewahren Sie den Sinn. Wenn sich ein Satz falsch anfühlt, erklären Sie warum, statt ihn stillschweigend in ein Versprechen zu verwandeln, das wir nicht halten können.

Sie können auch helfen, indem Sie jemandem zeigen, wie Monica funktioniert, durchdachtes Feedback teilen oder für den gehosteten Dienst bezahlen, wenn er Ihnen nützt. Finanzielle Unterstützung zählt, aber sie kauft keine Kontrolle über die Richtung des Produkts.

Und entfernen Sie bitte persönliche Informationen aus Beispielen. Eine nützliche Reproduktion braucht die Form des Problems, nicht die Krankengeschichte Ihres Cousins.

Tragen Sie etwas Überschaubares bei, erklären Sie es klar und geben Sie den Leuten Zeit zu antworten. Das ist ein sehr guter Anfang.
